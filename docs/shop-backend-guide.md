# Гайд: подключение backend к магазину

Статус: проект интеграции, **не реализованный API**. Ни маршруты `/api/shop/*`,
ни переменные `VITE_SHOP_*`, ни платёжный провайдер пока не подключены.
Этот документ не разрешает реальные списания, отправку писем или production-деплой.
Обзор UI: [shop.md](shop.md); инструкции агента: [AGENTS.md](../AGENTS.md).

## Текущее состояние

| Участок | Что есть сейчас |
| --- | --- |
| [Shop.tsx](../src/shop/Shop.tsx) | `checkout()` синхронно вызывает `createDemoOrder`, очищает корзину и открывает success |
| [cart.ts](../src/shop/cart.ts) | `CartItem { id, qty }`, `MAX_QUANTITY = 99`, локальная валидация, `DemoOrder` |
| [data.ts](../src/shop/data.ts) | 8 продуктов, цены в целых USD, `unit: setup/session`, тексты RU/EN |
| Хранение | `localStorage.aihub_cart`, без PII; заказ только в React-состоянии |
| [Contact API](../backend/contact-api/server.js) | `/health`, `POST /api/contact`, SMTP и Sheets; не сервер заказов |
| [Pages workflow](../.github/workflows/gh-pages.yml) | Статический frontend; сейчас передаёт только `VITE_BASE` и `VITE_CONTACT_API_URL` |

Contact API валидирует имя/email/телефон, не сохраняет состав заказа и не возвращает
order ID. Незнакомые поля корзины не становятся заказом. `Promise.all` для SMTP/Sheets
может завершиться частичным внешним успехом; повтор после ошибки может дублировать лид.
Его in-memory rate limit не является идемпотентностью или надёжным хранилищем.
CORS разрешает только `Content-Type`, не `Idempotency-Key`/`Authorization`.

15.10.2026 в 17:20 UTC `/health` и OPTIONS `/api/contact` вернули HTTP 503.
Это отдельная операционная проблема, не повод менять адрес на выдуманный.
До повторного использования сервиса восстановить его и проверить отдельно.
POST с контактами во время аудита не отправлялся. Подробности: [аудит](agent-paths-audit.md).

## 1. Согласовать режим

Сначала выбрать один сценарий; frontend не должен угадывать его по сетевой ошибке.

| Режим | Результат действия |
| --- | --- |
| demo | Только локальный пример, как сейчас |
| request | Сервер сохраняет заявку с товарами и контактами; без оплаты |
| payment | Серверный заказ, hosted checkout провайдера и подтверждённый webhook |

Практичный первый этап: `request`, если бизнесу нужна заявка на внедрение, а не
моментальная покупка. До `payment` согласовать страну/юрлицо, валюты, назначение
`setup`/`session`, налоги, возвраты, способ доставки услуги и выбранного провайдера.
Текущие единицы не означают подписку. Юридические тексты и правила обработки данных
согласует владелец бизнеса; этот документ не задаёт правовую политику.

## 2. Разделить ответственность

```text
shop.html -> Shop UI -> shop API client -> отдельный HTTPS backend -> БД заказов
                                                       -> outbox -> SMTP/CRM/Sheets
                                                       -> hosted checkout
провайдер оплаты -> подписанный webhook -> backend -> статус платежа в БД
```

Планируемые **новые** файлы: `src/shop/api.ts` (transport и runtime-валидация),
`src/shop/contracts.ts` (типы), `src/shop/CheckoutForm.tsx` (поля/состояния),
backend-модуль/сервис и миграции БД. Это предложение, таких файлов пока нет.
Нельзя размещать сервер или секреты в `public/` или рассчитывать на выполнение
Node.js внутри GitHub Pages.

Можно расширить существующий сервис или развернуть отдельный; выбор за владельцем.
При расширении обязательно сохранить контракт и тесты Contact API. Не переносить
обработку заказов целиком в текущий обработчик отправки письма.

Источник истины: серверный каталог с устойчивыми product ID, актуальностью,
валютой, целочисленной ценой в минимальных единицах и версией. Например,
1490 USD в текущем каталоге соответствует `149000` cents для USD.
Не импортировать `src/shop/data.ts` напрямую в Node backend: он зависит от UI-kit
и Vite-путей и не является серверным контрактом. Согласовать однонаправленную
синхронизацию каталога; локальные тексты/иконки могут оставаться во frontend.

Минимальные сущности БД: products, orders, order_items со снимком цены/названия,
idempotency_records, notification_outbox; для оплаты также payments и webhook_events.
Нужны транзакции, уникальные ограничения, миграции, backup и проверка восстановления.
Sheets/почта могут получать копию, но не заменяют реестр заказов.

## 3. Предлагаемый HTTP-контракт

Все маршруты ниже проектируемые. Зафиксировать их в OpenAPI/JSON Schema и контрактных
тестах до frontend-интеграции, включая выбранную модель сессии/авторизации.

| Метод и путь | Назначение |
| --- | --- |
| GET `/health` | Жив ли процесс; отдельно readiness БД/очереди |
| GET `/api/shop/catalog` | Версия каталога, активные ID, цены, валюта и единицы |
| POST `/api/shop/orders` | Валидация и атомарное сохранение заказа/заявки |
| GET `/api/shop/orders/:id` | Статус; доступ только владельцу или ограниченной guest-сессии |
| POST `/api/shop/orders/:id/checkout` | Только payment: идемпотентное создание платёжной сессии |
| POST `/api/shop/webhooks/:provider` | Только сервер провайдера, проверка подписи |

Нельзя сделать status endpoint общедоступным только потому, что order ID похож на UUID.
Для гостя согласовать ограниченный доступ через безопасную сессию или короткоживущий
непредсказуемый credential. Не размещать PII/долгоживущие credentials в URL и localStorage.

Пример **планируемого** тела создания заявки:

```json
{
  "items": [{ "id": 1, "qty": 1 }],
  "catalogVersion": "2026-10-15-v1",
  "customer": { "name": "Test Customer", "email": "customer@example.test", "phone": "" },
  "locale": "ru",
  "consent": { "accepted": true, "version": "privacy-v1" }
}
```

Заголовки: `Content-Type: application/json`, `Idempotency-Key: <random UUID>` и
согласованная авторизация/сессия. Пример не предназначен для рабочего Contact API.
Цена, итог, статус оплаты и произвольный callback URL от клиента не принимаются
как авторитетные значения. Ссылки возврата формирует сервер из allowlist.

Успешный ответ после сохранения в режиме request, HTTP 201:

```json
{
  "order": {
    "id": "ord_example",
    "createdAt": "2026-10-15T00:00:00Z",
    "mode": "request",
    "status": "requested",
    "currency": "USD",
    "totalMinor": 149000,
    "items": [{ "id": 1, "qty": 1, "unitPriceMinor": 149000 }]
  },
  "requestId": "req_example"
}
```

Для payment первоначальный заказ имеет статус `awaiting_payment`, не `paid`.
`checkoutUrl` возвращается отдельным endpoint после получения сессии провайдера.
Frontend должен проверять структуру ответа в runtime; `as Order` не является проверкой.

Ошибки имеют единый вид `{"error":{"code":"...","message":"..."},"requestId":"..."}`.
UI показывает локализованный текст по code, а не HTML/stack trace из ответа.

| HTTP/code | Поведение UI |
| --- | --- |
| 400 VALIDATION_ERROR | Ошибки полей; корзина и введённые данные остаются |
| 401/403 | Восстановить разрешённый доступ; не показывать чужой заказ |
| 409 CATALOG_CHANGED | Обновить цены/доступность и получить новое подтверждение |
| 409 IDEMPOTENCY_CONFLICT | Не переотправлять другой payload со старым ключом |
| 413 / 415 | Отклонить слишком большой запрос / неверный Content-Type |
| 429 RATE_LIMITED | Учитывать Retry-After, не запускать бесконечные повторы |
| 5xx / timeout | Исход неизвестен; проверить статус или повторить с тем же ключом |

## 4. Серверные инварианты

- Проверять ID, активность товара, целочисленные qty 1..99, число позиций и размер
  запроса. Повторы ID обрабатывать однозначно и лимитировать итоговую qty после объединения.
- Пересчитывать цены/валюту/итог только по серверному каталогу. Несовпадение версии
  не оплачивать молча: вернуть конфликт и новый расчёт для подтверждения пользователем.
- Хранить снимок позиций и версии согласия, время назначать на сервере.
- Идемпотентность хранить в БД по сессии/пользователю, операции и ключу с hash тела.
  Тот же payload возвращает тот же результат; другой payload с тем же ключом даёт 409.
- Конкурирующие повторы защищать unique constraint/транзакцией, не Map в процессе.
  Срок хранения ключей согласовать с допустимым окном повторов и восстановлением заказа.
- Заказ и outbox фиксировать одной транзакцией. Письмо/CRM отправлять с повторами
  отдельно; сбой уведомления не должен превращать сохранённый заказ в «не создан».
- Применять HTTPS, ограничения запросов, серверную авторизацию и безопасные логи.
  CORS не является аутентификацией. Для cookie-сессий нужны CSRF-защита и явные
  настройки credentials; не использовать wildcard origin. Общая основа:
  [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).

### Если нужна оплата

Карточные данные вводятся на hosted checkout выбранного провайдера, не в нашей форме.
Секрет провайдера и webhook secret хранятся только на сервере. Следовать документации
конкретного провайдера: проверить подпись по исходным байтам, допустимое время события,
merchant/account, order/payment ID, сумму и валюту. Уникальный event ID предотвращает
повторное применение. Хранить provider payment ID и использовать его идемпотентность
при создании сессии, включая сбой между вызовом провайдера и записью ответа в БД.

Redirect `success`/query-параметр не доказывает оплату. UI запрашивает серверный статус;
только подтверждённое событие или серверная сверка с провайдером переводит заказ в `paid`.
Обработать события не по порядку, повторную доставку, отмену и возврат. Не затирать
`paid` запоздалым `failed`; финансовые события и возвраты хранить отдельно.
Не выдавать услугу до серверного подтверждения; для потерянных событий нужна сверка.

## 5. Подключение frontend

1. Добавить API-клиент, типы и runtime-валидатор; разделить `DemoOrder` и серверный Order.
2. Загрузить каталог/версию с сервера. Если загрузка не удалась, можно показать
   локальные карточки, но нельзя принимать реальный заказ по устаревшим ценам.
3. Ввести состояние `idle -> submitting -> success/error/unknown`, поля контактов
   и согласия через UI-kit. Ошибки доступны скринридеру, фокус у первого неверного поля.
4. Перед запросом зафиксировать snapshot корзины и ключ идемпотентности. На время
   выполнения блокировать повторный submit; это UX, а не замена серверной защиты.
5. Использовать AbortController/timeout, но считать отменённый запрос потенциально
   выполненным сервером. Повтор того же намерения идёт с тем же ключом, не новым UUID.
6. Очищать отправленные позиции только после подтверждённого сохранения заказа.
   Не стирать изменения из другой вкладки: сверить snapshot либо вычесть отправленные
   количества. При ошибке/неизвестном исходе сохранить корзину и путь восстановления.
7. В request показать «Заявка принята», не «Оплачено». В payment показать серверный
   статус и ссылку на checkout; потеря redirect не должна терять доступ к заказу.
8. При неверной конфигурации live-режима показывать «Оформление недоступно», а не
   тайно вызывать `createDemoOrder`. Демо оставить отдельным явно обозначенным режимом.

Не сохранять customer/полный заказ с PII в `aihub_cart`. Сохранение идентификатора
незавершённого действия и ограниченного guest credential проектируется отдельно
с TTL, очисткой и учётом XSS, а не как общий бессрочный localStorage dump.

## 6. Конфигурация и CORS

Предлагаемые публичные build-переменные после реализации клиента:

```dotenv
VITE_SHOP_CHECKOUT_MODE=demo
VITE_SHOP_API_URL=https://shop-api.example.test
```

Домен примерный и не работает. Сейчас установка этих переменных ничего не меняет.
У `VITE_*` нет секретности: значения встраиваются в клиентский bundle.
[Vite: env и режимы](https://vite.dev/guide/env-and-mode).
В CI добавить явную передачу согласованных repository variables в шаг Build;
настройка переменной в GitHub без `env` в workflow не подключит её к сборке.
Backend-переменные DATABASE_URL, ключи провайдера, SMTP и webhooks передавать через
секреты runtime, не frontend Actions env и не `public/.well-known`.

Разрешённые frontend origins при текущем размещении:

```text
https://aihub.works
https://getcher123.github.io
```

Origin не содержит `/aihub-site/`. Для отдельного dev/staging добавить только
нужные localhost/staging origins. Для нового API проверить preflight с
`Content-Type, Idempotency-Key` и `Authorization`, если он используется.
Expose-Headers нужен для читаемых браузером Request ID/Retry-After.
`import.meta.env.BASE_URL` не является адресом API; не прибавлять к нему `/api/shop`.
Проверить CSP именно `shop.html`: политика `index.html` не наследуется другим HTML-входом.

## 7. Тесты и ввод в эксплуатацию

- Unit: ID/qty, объединение дублей, цены в minor units, переполнение, итог, версии.
- API: невалидное тело, удалённый товар, конкурентный двойной submit, рестарт процесса,
  тот же ключ/другое тело, чужой заказ, CORS/preflight, rate limit, сбой БД/outbox.
- Browser: обе локали, offline/timeout, сохранение корзины, смена корзины во второй
  вкладке, недоступный API, повтор после неизвестного результата, отсутствие PII в storage.
- Payment sandbox: неверная подпись, дубль и порядок webhook, неверная сумма/валюта,
  cancel, reload после redirect, повтор checkout и сверка потерянного события.
- Логи: requestId/orderId без полных контактов, credentials и платёжных данных.

[shop-smoke.mjs](../scripts/shop-smoke.mjs) проверяет **демо** и отсутствие write-запросов.
Сохранить этот сценарий для demo; для API создать отдельный staging smoke с тестовыми
данными и sandbox-провайдером. Не запускать write-smoke на production без разрешения.

Порядок выкладки: backup и миграции -> backend/health/readiness -> sandbox-тесты ->
сборка frontend с режимом request/payment -> проверка Pages root и subpath -> мониторинг.
Деплой backend не равен push сайта. Для отката отключить live checkout/вернуть frontend
версию, но сохранить БД, webhooks и обработку уже созданных заказов. Не удалять записи
и не запускать опасную обратную миграцию ради косметического отката.

Критерий готовности: одна пользовательская операция создаёт один устойчивый заказ,
повтор безопасен, цена серверная, доступ ограничен, UI честно показывает статус,
есть наблюдаемость и проверенный путь восстановления. До этого магазин остаётся demo.
