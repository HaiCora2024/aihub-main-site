## Как работает проверка

Форма консультации и checkout используют общий компонент Turnstile Managed.
Загрузка проверки начинается при фокусе или нажатии внутри формы, а также
при попытке отправки. Поддерживаются RU/EN, клавиатура, истечение проверки,
ошибка загрузки и повтор. Контакты и реквизиты остаются в состоянии React;
при ошибке проверки они не очищаются, но перезагрузка страницы их потеряет.

Токен передаётся только в `X-Turnstile-Token`. Он не попадает в JSON заявки,
хранилища браузера, SQLite или прикладные логи. Сервер обращается к Siteverify
с тайм-аутом 5 секунд и проверяет `success`, hostname и action:

| Endpoint | Action |
| --- | --- |
| `POST /api/contact` | `contact_submit` |
| `POST /api/shop/requests` | `shop_submit` |

Новая отправка требует действительной проверки. Тот же секретный ключ уже
принятой заявки возвращает её подтверждение, не требует нового токена и не
создаёт новых побочных действий. GET проверки статуса магазина остаётся
доступен по существующему Bearer-ключу, даже если виджет не загружается.

Ответы сохраняют прежние конверты: контактная форма `{ok:false,error:CODE}`,
магазин `{error:{code:CODE,fields},requestId}`. Дополнительные коды:

| Код | HTTP | Действие интерфейса |
| --- | --- | --- |
| `BOT_CHECK_FAILED` | 403 | Обновить проверку, сохранить поля |
| `BOT_CHECK_UNAVAILABLE` | 503 | Предложить повторить, сохранить поля |
| `INVALID_IDEMPOTENCY_KEY` | 400 | Исправить интеграцию клиента |
| `IDEMPOTENCY_CONFLICT` | 409 | Не создавать повтор автоматически |
| `RATE_LIMITED` | 429 | Соблюдать `Retry-After` |
| `CONTACT_DELIVERY_FAILED` | 503 | Повторить ту же контактную заявку |
| `CONTACT_DELIVERY_UNKNOWN` | 503 | Обратиться к оператору, не рассылать повторно |
| `CONTACT_UNAVAILABLE` | 503 | Не показывать успешную отправку |

## Повторы и доставка

Обе формы передают случайный `Idempotency-Key` длиной 32 байта в hex.
В контактной форме снимок отправки и ключ остаются в памяти вкладки для повтора.
При неизвестном сетевом результате форма повторяет прежний снимок; редактирование
заблокировано до результата. Значения формы в localStorage/sessionStorage не добавляются.
В магазине сохраняется прежняя схема восстановления без изменения состава корзины.

Контактные подтверждения находятся в отдельной SQLite-базе, не в shop outbox.
Сохраняются только хеш ключа, HMAC нормализованных полей, UUID, время и состояния
каналов `mail` / `sheet`. Текста формы и открытых контактов в базе нет.
Ключ с другим содержимым даёт 409. Одинаковые имя, email и телефон с новым
ключом объединяются в течение 10 минут независимо от URL и tracking-source;
для каждого ключа отдельно проверяется полный нормализованный снимок.
Записи и привязки ключей удаляются после
24 часов при запуске, обращениях и обслуживании раз в минуту.

Для каждого канала отметка `sending` записывается до внешнего вызова.
Завершённый канал не повторяется. Явный отказ (например, ошибка доступа Google
или SMTP-отказ) допускает повтор только неуспешного канала. Тайм-аут после
возможной отправки, неоднозначный ответ или незавершённое действие после
перезапуска переходят в `unknown`; автоматической повторной рассылки нет.
SMTP/Sheets не дают общей транзакции, поэтому результат `unknown` разбирает
оператор по почте, таблице и примерному времени обращения.

Для магазина тот же принцип применяется к outbox: неоднозначный SMTP-результат,
частичное принятие получателей и просроченный lease прерванной отправки получают
`failed / DELIVERY_UNKNOWN`. Остальные письма продолжают обрабатываться.
После разбора оператор может использовать существующий `shop:admin retry-mail`;
такой ручной повтор требует проверки уже доставленных писем. Явные SMTP-отказы
сохраняют существующий ограниченный механизм повторов.

Реестр подтверждений предназначен для одного экземпляра API. При потере БД
защита от ранее выполненных действий теряется; не удалять её для снятия ошибки.
При переносе требуется также HMAC-ключ, иначе старые отпечатки не проверяются.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `VITE_TURNSTILE_SITE_KEY` | Публичный sitekey, GitHub Repository Variable |
| `TURNSTILE_SECRET_KEY` | Рабочий secret key, секрет Amvera; не передавать в VITE |
| `TURNSTILE_ALLOWED_HOSTNAMES` | `aihub.works,www.aihub.works` |
| `TURNSTILE_ENFORCE` | `true` включает обязательную проверку новых отправок; по умолчанию `false` для переходного выпуска |
| `FORMS_TRUST_PROXY_HOPS` | Число подтверждённых proxy hops, по умолчанию 0 |
| `FORMS_TRUST_PROXY_CIDRS` | Проверенные адреса/CIDR доверенных прокси через запятую |
| `RATE_LIMIT_MAX` | Лимит контактной формы, по умолчанию 5 |
| `RATE_LIMIT_WINDOW_MS` | Общее окно ограничений, по умолчанию 900000 |
| `CONTACT_RECEIPTS_PATH` | В production `/data/forms/contact-receipts.sqlite`, локально `.local/contact-receipts.sqlite` относительно рабочей папки |
| `CONTACT_DEDUPE_KEY` | Необязательный секрет: 32 случайных байта в base64 |

Если `CONTACT_DEDUPE_KEY` не задан, сервер сам создаёт закрытый двоичный
`contact-receipts.sqlite.key` рядом с БД на persistent volume. Каталог 0700,
БД и ключ 0600. При существующей БД и потерянном ключе запуск прекращается,
а не создаёт новый несовместимый ключ. Ключ не выводится в логи и Git.

Проверка IP общая для двух форм. По умолчанию учитывается только адрес сокета.
Для доверия X-Forwarded-For нужны **обе** настройки proxy. Проверяются адрес
непосредственного peer и промежуточные доверенные hops, затем выбирается
адрес справа от подтверждённой границы. Произвольный левый элемент не используется.
Неверная цепочка возвращает адрес сокета. IPv4-mapped IPv6 нормализуется.
В runtime старый `SHOP_TRUST_PROXY_HOPS` заменён общими `FORMS_*` настройками.

Ограничения отдельных групп не смешиваются: контактные POST 5/15 минут,
shop POST 5/15 минут, shop status 120/15 минут. Карта ограничена 10000 записями,
истёкшие записи очищаются. При неизвестной цепочке ingress лимит по адресу
сокета может оказаться общим для посетителей; до включения подтвердить настройку.

## Подключение production

1. Создать бесплатный аккаунт Cloudflare и Managed-виджет `AIHUB forms` для
   `aihub.works`. Pre-clearance не включать. DNS переносить не требуется.
2. Разместить sitekey в переменной основного GitHub-репозитория, secret key
   в секрете Amvera; задать разрешённые production hostnames.
3. Подтвердить у Amvera фактическую цепочку ingress, зафиксировать адреса/CIDR
   и число hops в приватном операционном отчёте. Проверить два независимых
   клиентских адреса и запрос с добавленным ложным префиксом X-Forwarded-For.
   По одной наблюдаемой строке не разрешать широкие private CIDR.
4. Выпустить совместимый backend с `TURNSTILE_ENFORCE=false`, проверить persistent
   реестр и readiness. Затем опубликовать frontend с рабочим sitekey и совпадающей
   версией Privacy Policy `2026-10-28-security-v2`.
5. Проверить загрузку настоящего виджета. Для обоих actions проверить свежий
   токен командой ниже из защищённой среды с рабочим secret key. Затем задать
   `TURNSTILE_ENFORCE=true` и перезапустить API.
6. Проверить health/readiness, CORS, каталог и опубликованные формы. Реальные
   заявки, письма и строки Sheets для smoke не создавать. Полный путь доставки
   проверяется локально, либо отдельной разрешённой контрольной отправкой.

В каталоге `backend/contact-api`, где секрет и hostnames доступны через env:

```bash
npm run forms:verify -- contact_submit < /private/fresh-contact-token
npm run forms:verify -- shop_submit < /private/fresh-shop-token
```

Это прямые проверки Siteverify: они не создают заявки, БД, письма или строки
Sheets. Токен читается из stdin, в ответ выводятся только результат и action.
Для каждого вызова нужен новый токен; после проверки обновить виджет.
Значение secret key и токен не передавать в аргументах команд или отчётах.

Включение обязательной проверки блокирует новые запросы старых страниц без токена.
Пользователю потребуется обновить страницу; новый интерфейс объясняет ошибку
и сохраняет поля до перезагрузки. Принятые заявки доступны по прежним ключам.

Рабочий запуск запрещает официальные тестовые secrets при `NODE_ENV=production`.
Сборка запрещает dummy sitekeys вне явного тестового режима Vite `--mode test`.
Тестовый режим предназначен только для локальных проверок, не для Pages workflow.
Если `TURNSTILE_ENFORCE=true` и ключ/hostnames отсутствуют, API не запускается.
Сбой Siteverify при включённой проверке не открывает отправку автоматически.

Для отката в рамках согласованного выпуска можно отключить обязательность
проверки и убрать публичный sitekey из следующей frontend-сборки. Этот режим
снижает защиту; он не должен называться защищённым Turnstile. Не удалять реестр
подтверждений и не менять HMAC-ключ при обычном откате.


По умолчанию виджет и Siteverify детерминированно подменены для воспроизведения
ошибок, одноразовых состояний и работы клавиатурой; используются официальные

с официальным тестовым sitekey; Siteverify по-прежнему подменён, поэтому этот
режим не выдавать за проверку рабочего production secret key. `QA_BASE=/nested/`
проверяет BASE_URL. `QA_OUTPUT` задаёт каталог отчёта.
